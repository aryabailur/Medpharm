# MedTrack Simulator

**Role:** Node/tsx telemetry generator that drives GPS + temperature along a route and POSTs to Vayu's ingest endpoint, standing in for real hardware.
**One-liner:** Same JSON, same endpoint an ESP32 + DS18B20 + NEO-6M would use — swap the simulator for real hardware with zero server-side code change (§6.1, §6.2).

## 1. What it is / what it owns / what it does NOT own

**What it is:**
- A CLI/worker (`src/cli.ts`, run via `tsx`) that interpolates a shipment's position along a polyline, generates a temperature signal inside (or deliberately outside) a cold-chain band, and POSTs each reading to `backend/vayu-api`'s `POST /api/sensors/ingest` at 1-2 Hz (§6.1).
- The exact payload shape defined by `SensorIngest` in `@medtrack/contracts` — the same shape a real ESP32+DS18B20+NEO-6M device sends over the wire. This identity is the entire point of the module (§6.1, §6.2): *"same endpoint, same payload."*

**What it owns:**
- `src/index.ts` — the `run(options, injection)` entry point, and the `SimulatorOptions` / `ExcursionInjection` types.
- `src/cli.ts` (to be created) — parses CLI args, builds `SimulatorOptions`/`ExcursionInjection`, calls `run(...)`.
- Nothing else. It is a stateless script; it holds no database, no persisted run history.

**What it explicitly does NOT own:**
- `TelemetryPoint` storage, excursion detection/classification, or SSE push — all of that lives in `backend/vayu-api` (§6.1's pipeline diagram: ingest → write → SSE → webhook → excursion detector are all server-side, downstream of this module's POST).
- The webhook to Dhanvantari, HMAC signing, or any cross-app contract logic — that's `backend/packages/crypto` and the two `-api` servers.
- Route *creation* — routes are supplied to it (§10: 8-10 real corridors via OSRM, e.g. Mumbai-Nashik, Pune-Solapur), not generated by it.

## 3. CLI reference (target shape, once `src/cli.ts` exists)

| Flag | Maps to | Required | Notes |
|---|---|---|---|
| `--shipment-id` | `SimulatorOptions.shipmentId` | yes | Must be a real `shipmentId` (UUIDv7) the ingest endpoint recognizes |
| `--ingest-url` | `SimulatorOptions.ingestUrl` | yes | e.g. `http://localhost:4000/api/sensors/ingest` |
| `--duration` | `SimulatorOptions.durationSeconds` | yes | Demo shipments run 60-120s (§6.1, §11) |
| `--temp-band` | `SimulatorOptions.tempBandC` | yes | e.g. `2,8` for a cold-chain product |
| `--device-id` | `SimulatorOptions.deviceId` | no | Defaults to a generated simulator device id |
| `--route` | route polyline source | yes | File path or named corridor to a `[lng, lat]` array |
| `--inject-excursion` | builds an `ExcursionInjection` | no | Enables the 2:30 demo beat (§11) |
| `--excursion-at` | `ExcursionInjection.atProgressPct` | with `--inject-excursion` | 0-1 fraction of route progress |
| `--excursion-peak` | `ExcursionInjection.peakTempC` | with `--inject-excursion` | e.g. `14.2` |
| `--excursion-duration` | `ExcursionInjection.durationSeconds` | with `--inject-excursion` | **Must be ≥ 60s** or the hysteresis guard correctly ignores it as noise (§6.1) |

`run(options: SimulatorOptions, injection?: ExcursionInjection): Promise<void>` remains the single library entry point exported from `src/index.ts` — the CLI is a thin arg-parsing wrapper around it, nothing more.

| Part | Owns |

| **Part 2** | `src/temperature.ts` (temp model + excursion injection, new file), `src/carriers.ts` (carrier personality profiles, new file) |

### Shared — coordinate before editing

| File | Why it's shared | Rule |
|---|---|---|
| `src/index.ts` | Both parts consume/extend `SimulatorOptions` and `ExcursionInjection`, and both wire their module into `run()` | **Neither part edits alone.** Agree on the final shape of both interfaces before either part starts; whoever needs a field the other doesn't have yet adds it here first, in a one-line PR, before building against it. |

Concretely: Part 1 needs `SimulatorOptions` (route, duration, ingestUrl, deviceId) to build the interpolation + POST loop. Part 2 needs `SimulatorOptions.tempBandC` and `ExcursionInjection` to build the temperature model. Both read the same two interfaces — if either part needs to *change* a field (not just read it), post in chat/PR description before editing `src/index.ts`, since a silent field rename breaks the other person's half mid-build.

### Part 1 — Route interpolation + CLI + ingest loop (critical path)

This is the skeleton everything else plugs into — nothing runs end-to-end without it.

| Task | Files created | Phase | Depends on |
|---|---|---|---|
| Position interpolation along `route: Array<[lng, lat]>` by elapsed time fraction | `src/route.ts` | 4 | — |
| `POST` loop to `ingestUrl` at 1-2 Hz using `SensorIngest` shape from `@medtrack/contracts` | `src/ingest.ts` | 4 | route interpolation |
| `src/cli.ts` — arg parsing, builds `SimulatorOptions`/`ExcursionInjection`, calls `run()` | `src/cli.ts` | 4 | `src/index.ts`'s exported types (read-only dependency) |
| Wire `run()` in `src/index.ts` to call route interpolation + ingest loop, replacing the `throw new Error('Phase 4')` stub | `src/index.ts` (the `run` function body only) | 4 | route.ts, ingest.ts complete |
| Stop condition at end of route / duration | `src/route.ts` or `src/ingest.ts` | 4 | interpolation |

### Part 2 — Temperature model + excursion injection + carrier personalities

| Task | Files created | Phase | Depends on |
|---|---|---|---|
| Baseline temp model: hold inside `tempBandC` with light noise | `src/temperature.ts` | 4 | `SimulatorOptions.tempBandC` type (read-only) |
| Excursion injection: ramp to `peakTempC` at `atProgressPct`, hold `durationSeconds`, recover | `src/temperature.ts` | 4-5 | baseline model, `ExcursionInjection` type (read-only) |
| **Duration guard note:** injected excursions must last ≥ 60s / ≥3 consecutive readings at 1-2 Hz, or the server-side hysteresis detector correctly discards them as noise (§6.1) — this is a design constraint on the injection function, not a bug to fix later | `src/temperature.ts` | 4-5 | injection ramp above |
| Carrier personality profiles: 4-5 distinct excursion profiles (one chronically late, one with a failing reefer, etc.) per §10 | `src/carriers.ts` | 5 | temperature model |
| Personality-driven noise/trend parameters feeding into the temp model | `src/carriers.ts`, `src/temperature.ts` | 5 | carrier profiles |

Once both parts are done, integration is: Part 1's `ingest.ts` POST loop calls Part 2's `temperature.ts` function each tick to get the current `tempC` value, alongside Part 1's interpolated `lat`/`lng`. That call site lives in `src/index.ts`'s `run()` body — coordinate the function signature (`getTempAtProgress(progressPct, options, injection?): number` or similar) before either side hard-codes an assumption about it.

## 6. Non-negotiables / gotchas

- **Payload identity is the whole point.** The simulator must produce exactly the `SensorIngest` shape (`{ deviceId, shipmentId, ts, lat, lng, tempC, humidity?, battery? }`, §6.1) — do not add simulator-only fields or the "zero code change to swap in hardware" claim becomes false.
- **Demo shipments run 60-120 seconds** (§6.1, §11) — the interpolation and injection timing must work correctly at this short duration, not just over a long synthetic run.
- **The excursion injection must clear the hysteresis guard**: ≥3 consecutive out-of-band readings or ≥60 seconds, or the server's excursion detector will — correctly — treat it as sensor noise and the 2:30 demo beat will silently not fire (§6.1). Test this specific timing before demo day, not during it.
- **1-2 Hz POST rate**, not faster. This matches the assumed cadence of both the ESP32 hardware path and the server's throttled webhook-to-Dhanvantari cadence (10s, §5.1) — going much faster just wastes ingest calls without changing what the UI shows.
- **Do not let the simulator talk to Dhanvantari, Nidana, or any endpoint other than Vayu's `/api/sensors/ingest`.** All downstream fan-out (SSE, webhook, excursion detection) is Vayu's job per the pipeline in §6.1 — the simulator's contract is a single POST.
- **This package must work standalone without hardware.** Per §6.2: "If you don't [get hardware working], the simulator alone is fully sufficient. Do not let hardware block software progress." Do not add a hard dependency on any hardware-only tooling.
- **Carrier personalities should be genuinely differentiated**, not cosmetic (§10): "Clean data makes every downstream feature look fake." A carrier profile with no real failure signature gives the RCA agent nothing true to find.
